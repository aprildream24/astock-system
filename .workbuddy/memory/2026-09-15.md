### ★ 真凶 B（真正的实盘杀手）：腾讯 K线域名 HTTP 501 拖死抓取

逐源实测（4 只真实票）：
| 源 | 结果 | 耗时 |
|---|---|---|
| `_kline_one_em` (push2his) | 全失败 RemoteDisconnected → 熔断 | 0.3–4.3s |
| `_kline_one_tx` (**ifzq.gtimg.cn**) | **全失败 HTTP 501 Not Implemented** | **6–15s** |
| `_kline_one_sina` | ✅ 成功 20 根 | 0.3–0.5s |

链式后果：
1. 腾讯 K线域名已迁到 **`web.ifzq.gtimg.cn`**（200/0.41s，数据正常），
   裸域名 `ifzq.gtimg.cn` 端点下线返 501；
2. 而熔断码只有 `(403,429,418)` ⇒ **501 永不被熔断**，
   被当普通失败重试 `retries=2` + 指数退避 ⇒ **单票白等 6–15 秒**；
3. 全市场 ~4900 只 ⇒ 抓取远超 timeout ⇒ 第 8 步「构建+推送」skipped

修法（`pipeline/core.py`）：
```python
TX_HOSTS = ("web.ifzq.gtimg.cn", "ifzq.gtimg.cn")   # 候选列表，不得写死单点
DEAD_CODES = (404, 410, 501)   # 端点级失效：不重试、计入熔断
```
- `fetch_text`：`DEAD_CODES` **立即抛出**，不走退避 sleep；
- `_kline_one_tx`：逐域名尝试，BanBlocked 也不行就换下一个；
- `kline_batch`：仅当**全部**候选域名都熔断才放弃。

**实测修复效果：100 只 → 11.1s / 100% 成功 / 9.0 只每秒
⇒ 全市场 4937 只 ≈ 9.2 分钟**（此前必然超时）。

## 第五轮：又挖出一个**循环依赖**闸门（close 可能被自己挡住）

在等抓取时探测闸门，发现：

```
build.data_ready_for(con, '2026-09-15')  -> (False, '非交易日')
core.is_trading_day_cross(con,'2026-09-15') -> (False, '指数日K无此日期')
```

而 `holiday_cal.is_trade_day('2026-09-15')` = **True**（日历本身是对的）。

根因：`trade_calendar(con)` **完全由 `klines` 表里 `sh000001` 的日期推导**
（260 条，最新 09-14）。于是：
- `is_trading_day_cross` 第一关就是 `date in trade_calendar(con)`；
- `data_ready_for` 第一关同样是 `date not in trade_calendar(con)` → "非交易日"。

⇒ **当日指数K线未入库时，两个闸门都会把"今天"判成非交易日**，
`close` 打印「拒绝构建（指数日K无此日期/非交易日）」→ `return None`（rc=0）。
**这是"闸门依赖被闸门管控的数据"的循环依赖。**

注意与第四轮真凶 B 的叠加关系：域名 501 导致**抓取超时**，
抓取超时 ⇒ 指数K线永不入库 ⇒ 闸门永远判"非交易日" ⇒ 即使抓取侥幸跑完，
`close` 仍可能被挡。两者是**串联**的，必须都修。

待验证：抓取成功入库 `sh000001@2026-09-15` 后，闸门是否自动放行
（若是，则本次只修数据源即可；若仍有窗口期风险，需给闸门加
「日历回退」——用 `holiday_cal` 兜底而非纯 K线推导）。
