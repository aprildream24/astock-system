### 「260 根」是什么意思（答用户问）
`--days N` = **每只票往回拉 N 个交易日的日K**（每天 1 根）。
260 根 ≈ 一年历史（A 股年均 ~243 个交易日）。

### 为什么降到 40：全仓回看深度审计（硬数据）
脚本扫描 `pipeline/*.py` 全部切片表达式，真实结果：

| 回看 | 位置 | 用途 |
|---|---|---|
| **30** | `engines.py:262` `rows[-30:]` | **最大真实回看** |
| 20 | `engines.py:420` `rets[-20:]` | 波动率比 |
| 20 | `engines.py:140` `vols[-20:]` | 量比 |
| 20 | `engines.py:123` `dailies[-20:]` | 加速度 |
| ≤10 | 其余全部 | 展示/截断 |

即「**用 30~32 根、拉 260 根**」= 白耗约 8 倍解析/写库量。
40 根留 +33% 余量（40 vs 30）。

## 「run 全绿但零推送」第二类静默失败（本轮新挖）

### 现象
CI run `34994141036`（16:18 触发）**全 14 步 success**，但：
- 第 10 步「构建+推送」耗时 **0 秒**
- 远端账本未新增任何记录（仍停在 10:58 / 12:33）
- 用户**零感知** —— 又是"我这边全绿，用户啥也没收到"

### 排查中踩的坑（我自己误判两次）
1. ❌ **误判一**：以为 dispatch 的 `{task: close}` 被丢弃。
   理由：runs API 返回 `inputs: {}`。
   **真相**：runs API **根本不暴露 inputs 字段**（实测 key 列表里没有）。
   所有历史 run 都显示 `{}`，包括 10:58 那条真发了推送的。
   → **教训：不要用 runs API 的 inputs 判断 dispatch 参数是否送达。**
   想确认 task 只能靠**副作用物证**（账本条目 / 站点日期 / 步骤耗时）。
2. ❌ **误判二**：以为 build 就绪闸门拒绝了。
   实测本地 `data_ready_for(con,'2026-09-15')` = `(True,'K线就绪')`，
   `klines@09-15=4588`、`snapshot@09-15=5559` —— 闸门完全放行。

### 真因：日级保险丝按设计拦截（**不是 bug**）
`notifier._daily_sent(con, 'build_close', '2026-09-15')` 在 CI 上为 **True**
（10:58 已 sent）⇒ `push()` 直接返回 `{sent: False, dedup: True, daily_gate: True}`
⇒ build 早退，rc=0，**1 秒内结束**。16:32 再触发一次仍被拦。

这是 2026-09-14 定调的**不可回退设计**：同 mode 同日期一天最多一条，
防 GitHub cron 幽灵延迟重复推送。**行为正确**。

### ★ 但暴露一个真实缺陷：账本「本地/远端分叉」
实测两边不一致：
| | 条目数 | 含 09-15 build_close |
|---|---|---|
| 本地 `dist/push_ledger.json` + DB 表 | 14 | **否**（只有 09-14） |
| 远端仓库 `dist/push_ledger.json` | **3** | **是** |

两个后果：
1. **本地永远复现不出 CI 的拦截行为** —— 又一类"本地绿、CI 不一样"。
2. 远端账本被**激进裁剪到只剩 3 条**（本地 14 条），
   而 `_daily_sent` 依赖它做跨 run 判定 → 一旦被裁掉当日记录，
   保险丝就会**失效**，重复推送会回来。
   → 需确认裁剪逻辑（`clear_dedup.py` / `push_ledger_sync.py`）的保留窗口。

### ③ CI 缓存膨胀（已修 + 已清理）

**实测 API `GET /actions/caches?per_page=100`**（此前一直是推测，这次拿到硬数据）：
15 条、合计 **469.3 MB**，呈清晰增长曲线：3.7 → 7.0 → **42.9 → 44.3 MB**。

**"44 MB 存不下 177 MB 数据库"这个旧判断是错的**：Actions 缓存是压缩存储。

实测 `gzip -6` market.db：177.0 MB → **52.6 MB（29.7%）**，7.1 秒。

Actions 用 zstd（比 gzip 略优）→ 44.2 MB **完全合理，缓存是完整的**。

**真问题是 key 含 `run_id`** → 每 run 新增一份，永不复用：

`key: market-db-${{ github.run_id }}` + `restore-keys: market-db-`。

**修法**：
- 拆 `actions/cache/restore@v4`（id: cache-db，`key: market-db-v2`）
  + workflow 末尾 `actions/cache/save@v4`（同 key，**覆盖写同一条目**）
- `if: always()` 保证抓取失败也存库
- **已清理**：删 14 条旧缓存，保留最新 1 条 → **释放 425.0 MB**（469.3 → 44.3 MB）

### ★ 归档经验（跨项目可复用）

1. **`/actions/runs/{id}/logs` 可用，`/jobs/{jid}/logs` 403** —— 排 CI 挂的首选入口
2. **测试禁止依赖工作区真实数据**（账本/DB/配置）—— 一律 mock 或隔离到临时路径；
